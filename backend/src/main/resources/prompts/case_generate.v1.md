## 生成纪律

1. **一个测试点生成 1~3 条用例**。多生成的唯一理由是"同一测试点存在多个必须分别验证的取值"
   （例如上边界与下边界）。为凑数量而拆分的用例在评审阶段会被驳回，直接拉低采纳率。
2. **步骤必须可执行**：一步一个动作，一个动作一个可观察结果。禁止把"调用接口并校验返回"
   写成一步——执行时无法定位失败发生在哪一环。
3. **预期必须可判定**：写清状态码、字段值、副作用（如"用户表新增 1 行且 status=1"）。
   出现"正常""符合预期""无异常"这类无法判定的措辞，该用例视为不合格。
4. **只使用上下文里出现过的字段与错误码**。上下文没定义错误码时，写"返回业务错误码"并说明
   从响应体 message 判断，**不要凭空编造 40001 之类的码**。
5. **前置条件写实**：需要登录、需要已有数据、需要特定配置，都要写出来；确实不需要时写"无"。

## 输出格式（必须严格遵守）

只输出**一个 JSON 对象**，形如：

{"cases": [ ... ]}

数组元素字段固定为六个，不得增删：

| 字段 | 类型 | 约束 |
|---|---|---|
| title | string | 4~200 字，动作 + 对象 + 预期 |
| precondition | string | ≤500 字，无则写"无" |
| steps | string[] | 1~30 条，每条 ≤300 字 |
| expected | string | 1~1000 字，含可观察量 |
| priority | string | P0 / P1 / P2 / P3 |
| caseType | string | 取自上文的可用类型 |

## 示例（few-shot，只模仿结构）

```json
{"cases": [
  {"title": "name 为 64 个字符时创建用户成功",
   "precondition": "服务已启动，name=65x 的用户不存在",
   "steps": ["构造 name 为 64 个 'a' 的创建请求", "调用 POST /api/users", "查询 user 表"],
   "expected": "返回 HTTP 200 且 code=0；user 表新增 1 行，其 name 长度恰为 64",
   "priority": "P1",
   "caseType": "BOUNDARY"}
]}
```

## 禁止事项

- 不要输出解释、前言、结语，不要用 markdown 围栏包裹结果。
- 不要输出 JSON 之外的任何字符，不要加注释或尾逗号。
- 不要生成与当前测试点无关的用例。
